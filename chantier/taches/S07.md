# S07 · Journal à empreintes (tâche pour Codex)

Lis d'abord `AGENTS.md` et `docs/REGLES.md`. Fais exactement ce qui suit, rien d'autre.

## Objectif

Un journal en ajout seul, dans `packages/core/src/journal/`, où chaque ligne est liée à la précédente par son empreinte SHA-256. Toute ligne modifiée, supprimée ou intervertie doit être détectée. Le journal servira à tout le socle : envois et refus d'envoi, lectures de fiches, fusions.

## Ce qu'il faut écrire

1. `packages/core/src/journal/types.ts`
   - `JournalEntry` : `seq` (entier, commence à 1), `at` (date ISO 8601 en UTC), `type` (texte, par exemple `message.refuse`), `actor` (identifiant interne, par exemple `agent:12` ou `systeme`), `subject` (identifiant interne ou `null`), `data` (objet JSON d'identifiants internes et de valeurs simples), `prevHash` (64 caractères hexadécimaux, 64 zéros pour la première ligne), `hash`.
   - `JournalStore` : interface avec `append(entry)`, `last()`, `all()`, `bySubject(subject)`, `byPeriod(fromIso, toIso)`. Toutes asynchrones, pour pouvoir brancher plus tard Cloudflare D1.
2. `packages/core/src/journal/hash.ts`
   - JSON canonique : clés triées à tous les niveaux, sans espaces.
   - `hashEntry(entrySansHash)` : SHA-256 hexadécimal du JSON canonique de `{seq, at, type, actor, subject, data, prevHash}`, avec l'API Web Crypto (`crypto.subtle.digest`), qui marche dans Node 22 et dans Cloudflare Workers. Aucune dépendance nouvelle.
3. `packages/core/src/journal/journal.ts`
   - `appendEvent(store, input, now)` : `input` contient `type`, `actor`, `subject`, `data` ; `now` est une fonction qui rend la date, pour les tests. Calcule `seq`, `prevHash` et `hash`, puis appelle `store.append`.
   - Refuse, avec une erreur claire, un `data` qui contient une donnée personnelle en clair : une valeur texte qui ressemble à une adresse mail ou à un numéro de téléphone français ou international. Le journal ne garde que des identifiants internes.
   - `verifyChain(entries)` : rend `{ ok: true }` ou `{ ok: false, brokenAt, reason }`, où `brokenAt` est le `seq` de la première ligne fautive.
4. `packages/core/src/journal/memory-store.ts` : une version en mémoire de `JournalStore`.
5. `packages/core/src/journal/sqlite-store.ts` : une version de `JournalStore` sur une base SQLite passée en paramètre. Définis dans `src` un petit type avec `exec(sql)` et `prepare(sql)`, comme `DatabaseSync` de `node:sqlite`, sans importer `node:sqlite` dans `src` : le même code devra tourner plus tard sur Cloudflare.
6. `db/migrations/0002_journal.sql` : table `journal` (`seq INTEGER PRIMARY KEY`, `at TEXT NOT NULL`, `type TEXT NOT NULL`, `actor TEXT NOT NULL`, `subject TEXT`, `data TEXT NOT NULL`, `prev_hash TEXT NOT NULL`, `hash TEXT NOT NULL UNIQUE`), index sur `subject` et sur `at`. SQL compatible D1 et SQLite.
7. `packages/core/src/index.ts` : exporter ce qui est utile du journal.

## Tests attendus, dans `packages/core/test/journal.test.ts`

- trois lignes ajoutées, `verifyChain` rend `ok` ;
- la ligne 2 modifiée après coup : détectée à 2 ;
- la ligne 2 supprimée : détectée ;
- les lignes 2 et 3 interverties : détectées ;
- `bySubject` et `byPeriod` rendent les bonnes lignes, dans l'ordre ;
- les mêmes tests passent avec la version en mémoire et avec la version SQLite, sur une base en mémoire où la migration `0002_journal.sql` est appliquée. Pour la base, utilise `describeWithSqlite` et `openMemoryDatabase` de `packages/core/test/sqlite.ts` : si ton environnement n'a pas Node 22, ces tests sont sautés chez toi et tournent sur GitHub ;
- un `data` avec une adresse mail, puis avec un numéro de téléphone, est refusé. Ces deux tests portent `[R13]` dans leur nom.

Les jeux de test sont inventés.
